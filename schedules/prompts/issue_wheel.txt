=== GOVERNANCE OF EVERY DISPATCH ===

A `Workflow` script cannot call the `Agent` tool and has no shell/fs access — it can fan out only

model-pin gate, no pacer lease). Every `Workflow` script this job invokes (P1 TRIAGE) is therefore

RULE G5 — PACER-DENIAL BRANCH. A `pretooluse_task.py` → `agent_budget.py gate` denial on any P3
(write-agent) or P2/LANE-RECIPE (lane-agent) dispatch is NEVER retried and NEVER silently dropped:
  * A denial on a P3 write-agent dispatch (`board-steward`): append the item to the ledger's
    `pending_mutations.items` with `defer_reason: "pacer-denied"` (a distinct reason code from any

  * A PIN denial (`pin-tier-mismatch`/`unpinned-agent-type`/any `model_pin_gate.py` reason) is

dirty-check — it is NOT item-scoped in its trigger surface. Pre-commit stashes the WHOLE tree
regardless of pathspec, so this check's trigger surface remains "anything outside this item's own
set," i.e. potentially the rest of the entire repository. This is correct, not over-firing: a
single stale, unrelated dirty file left over from another session genuinely WOULD be caught in
this item's own eventual commit's whole-tree stash, so parking on it is the right call. But it
also means a single long-lived unrelated dirty file CAN still park every candidate lane whose own
scope doesn't happen to include that file, night after night, until the dirt is cleared — this
check does not eliminate that scenario, it makes it VISIBLE (via the `peer_dirt_parks` heartbeat
count below) rather than leaving it as an invisible starvation.

Heartbeat additions for this check: `peer_dirt_parks` (count of items this run parked under
`peer-dirt-out-of-scope`) as a new additive HEARTBEAT CONTRACT key — never a new
`lanes_zero_reason` enum value; the per-item `park_reason` field already carries arbitrary reason
strings exactly as it carries `stale-superseded`/`already-landed`/etc. today.

(b) PRE-FLIGHT BEFORE SPEND — 5 checks, all must PASS; a non-zero exit / timeout / unparseable
output is a FAIL of that check ⇒ PARK `preflight-unverifiable`. A pre-flight park is never a
strike.
  1. ISSUE STATE — `gh issue view <issue> --json state,labels,title,body,comments`; must be OPEN;
     a `duplicate`/`wontfix` label or a "superseded by #M"/"folded into #M"/"duplicate of #M"/
     "resolved in <sha>" marker ⇒ PARK `stale-superseded` naming #M.
  2. ALREADY LANDED — `git -C $WHEEL_REPO log --all -i -n 50 --format="%h %s" --grep="\(Refs\|Fixes\|Closes\|Resolves\) #<issue>\([^0-9]\|$\)"`.
     `Refs` counts as landed. Any output ⇒ PARK `already-landed`. An OPEN issue whose fix already
     landed is still a park — never re-implement; the close path (P3) handles it.
  3. PATHS — every declared path exists, or sits under an existing parent; PARK `stale-paths` only
     when the parent is also missing.
  4. ALREADY VERIFIED — RETIRED 2026-09-20 together with the tracker (`WHEEL_TRACKER_REL` is no
     longer set, and the tracker HTML plus its `*_archive*.html` siblings were deleted 2026-09-16 —
     launch readiness now lives in GitHub issues). Do NOT look for tracker or archive files. An issue
     whose work is already done is caught by check 2 (ALREADY LANDED) and by its own GitHub state;
     this number is kept so checks 5+ keep their numbering.
  5. FRONTEND — decided HERE, before any isolated build is spent. Any declared path with a
     `frontend` path segment or under `shared_frontend/` ⇒ PARK `no-isolated-frontend-runner`. A
     harness worktree has NO `node_modules` (gitignored, never copied), so node/npm/vitest/tsc
     suites cannot run in isolation at all, and this job never runs an item's tests in the main
     tree to compensate. This is the pre-flight-before-spend absorption: deciding it at build time
     burns an isolated build for a park.

(c) CLAIMS — the claim-release-before-commit sequencing, with its mechanical WHY carried inline.
The CLAIM SET is defined ONCE and used verbatim at (e).4, (e).5's guard, and the commit pathspec:
the ENUMERATED SET from (e).1 PLUS `.secrets.baseline` — never the item's declared queue paths,
which name only source files and omit the tests, leaving them unclaimed and un-dirty-checked.
Command: `python3 ~/.claude/hooks/file_claims.py claim-check wheel-$WHEEL_SLUG-<issue>
<CLAIM_SET_ABS>` — CLAIM_SET_ABS uses `$WHEEL_REPO/<relative path>` for EVERY member, including
`.secrets.baseline` (see SEC-FIX below for why). The CLI's only verbs are `status`, `claim-check`,
`release`, `reset`, `doctor` — there is NO `claim` verb, and a mistyped verb prints usage to
stderr and STILL exits 0. The only evidence of a claim is `claim-check` itself printing
`OK claimed N path(s)`. Exit 1 = CONTESTED ⇒ PARK (nothing claimed, nothing to release). Exit 2 =
wrong arguments ⇒ fix the command, never proceed as if claimed.
Re-issue the identical `claim-check` every time the 300s TTL lapses, from (e).4 through the END of
(e).8 — including across the multi-minute review, the highest-risk window of the whole item,
because the patch is applied and staged in the shared tree throughout it.
RELEASE as the FIRST action of (e).9, immediately before the commit, and in a guaranteed-exit path
on EVERY park branch. WHY THE RELEASE MUST PRECEDE THE COMMIT: gate 4 claims the commit's own
paths under a different `agent_id` (the commit call's `tool_use_id`), and `find_contest` skips
only records whose `agent_id` equals its own — so a claim still held as `wheel-$WHEEL_SLUG-<issue>`
contests the wheel's own commit, which is then denied after a ~45s poll, and (e).8c's "retry the
identical command" livelocks until the 300s TTL silently expires. Gate 4's own per-commit claim
plus the per-repo commit mutex protect the commit window; the manual claim covers (e).4 through the
end of (e).8 and nothing beyond.

SEC-FIX — the cross-repo `.secrets.baseline` collision. `file_claims.normalize_path` strips only
`./` and trailing `/` and never absolutizes; `paths_overlap` string-compares. So CSA's
`.secrets.baseline` and Agency's are the same claim key, and whichever repo integrates second
would park every lane `commit-contested` after 3×45s retries. FIX: this job emits ABSOLUTE paths
in its CLAIM SET, always, including `.secrets.baseline` — `normalize_path` leaves an absolute path
intact, and `paths_overlap`'s prefix rule then correctly separates the two repos' baseline files.
CAVEAT (two spellings of the same set): the `git status --porcelain` clean-guards in (e).4/(e).5
must use the RELATIVE form (`CLAIM_SET_REL`) under `git -C $WHEEL_REPO` — git pathspecs are
repo-relative — while `file_claims.py` always gets `CLAIM_SET_ABS`. Never conflate the two. This
absolute-path fix also weakens this job's own contest detection against a peer session claiming
the SAME file with a relative path — accepted deliberately: the residual exposure is bounded by
the (e).4/(e).5 `git status --porcelain` clean-guards, which independently catch a concurrent
peer edit regardless of whether `file_claims.py` detected the contest, so a collision degrades to
a PARK on the guard, never a corrupted commit.

(c2) PLAN — required only above a threshold, decided BEFORE (d) BUILD so a required plan is never

or empty ⇒ treat as spanning 2+ directories (fail toward REQUIRING a plan — the safe direction);

  the declared `paths` + `.claude/oversight/dev-runtime.md`, writes it with the Write tool to

  Dispatch `plan-reviewer` (opus-pinned since the operator retired fable pins on 2026-09-24 — dispatch it BARE,

  --plan <path>` or `--blockers <n>` — log-only, blocks nothing mechanically.
  `--blockers <n>` ⇒ PARK the lane `plan-rejected`, with the plan path in the heartbeat. Do NOT
  attempt to talk the count down — the plan bar is completeness, not coherence; an unattended
  session must not re-argue a reject.
  When NOT required: proceed directly to (d), no plan artifact, no `plan-reviewer` dispatch.

(d) BUILD IN ISOLATION — six sub-steps, this exact order:
  1. SNAPSHOT THE MAIN TREE FIRST, before dispatching any sub-agent. Order is load-bearing: the
     implementer is NOT confined (the repo's `settings.local.json` with `Bash(*)` is copied into
     its worktree), so a baseline taken after it returns would bake in any main-tree write it
     made, making the leak undetectable forever. In the SAME step, BEFORE dispatching `implement`:
     copy every file the item's declared `paths` name that already EXISTS on disk to
     `<RUN_SCRATCH>/<wave>/prefix/<flattened-path>` (a scratch location
     outside both the main tree and the worktree — `cp`, not a git verb; gate 1 blocks `checkout
     --`/`restore --worktree`, and this scratch copy is what makes FALSIFIABILITY at (d).5
     possible without either). This is the pre-fix baseline the test-writer restores from below —
     take it now, before any dispatch touches the file, or it is not a genuine pre-fix baseline.
  2. DISPATCH `implement` with `isolation: "worktree"`. Its prompt MUST require its report to END
     with the literal output of `git rev-parse --show-toplevel` and
     `git status --porcelain -z -uall`, both from its own cwd. That reported toplevel line is the
     ONLY sanctioned way to learn `<worktree>` — a report without it ⇒ PARK
     `worktree-path-unreported`. NEVER infer the worktree by listing `.claude/worktrees/` — stale
     worktrees from unrelated work commonly live there, and integrating one of their diffs would
     land someone else's unreviewed changes wholesale.
  3. VALIDATE THE TOPLEVEL — must equal `<worktree>` and must NOT be `$WHEEL_REPO` (the harness
     removes a worktree the sub-agent left unchanged) ⇒ else PARK `no-changes/worktree-gone`.
  4. VALIDATE NON-EMPTY — empty porcelain ⇒ PARK, never enter (e): an empty patch yields an empty
     review and a failing commit, burning strikes on a phantom.
  5. DISPATCH `test-writer` WITHOUT isolation, told explicitly: repo root is `<worktree>`; read
     `<worktree>/.claude/oversight/dev-runtime.md`; create/edit files ONLY under `<worktree>/`;
     run every python test as
     `bash -lc 'cd <worktree> && PYTHONPATH=<worktree> $WHEEL_VENV_PYTHON -m pytest <tests>'` —
     the MAIN TREE's interpreter with the worktree as cwd and PYTHONPATH, because a worktree has
     no `.venv` and no `node_modules` and a bare `pytest` there resolves to a Homebrew interpreter
     with none of the project's dependencies. `$WHEEL_VENV_PYTHON` comes from `wheel_repos.json`'s
     `venv_python` field for this slug. ALSO require, in this same dispatch, the FALSIFIABILITY
     proof — a green suite alone never proves the new test actually exercises the fix. FIRST, in
     the WORKTREE, copy the CURRENT (fixed) content of each declared path to a SECOND scratch
     location, `<RUN_SCRATCH>/<wave>/postfix/<flattened-path>` (plain `cp`,
     taken now, before anything is overwritten). THEN restore each pre-fix source file from (d).1's
     scratch copy at `<RUN_SCRATCH>/<wave>/prefix/<flattened-path>` (plain
     `cp` — NEVER a git verb of any kind, not even `git checkout -- <path>` run inside the
     worktree: gate 1's `block_branch_ops.py` tokenizes the git subcommand alone and blocks
     `checkout` unconditionally — and `restore` in every form except its narrow `--staged`/`-S`
     spelling with no `--worktree`/`-W` — regardless of `-C`/cwd/worktree; there is NO
     main-tree-vs-worktree distinction anywhere in that gate), re-run EXACTLY the new
     test, and require the VERBATIM RED summary line proving it FAILS against the pre-fix content.
     THEN restore the fixed content back with a plain `cp` from the `postfix/` scratch copy taken
     above (never `git checkout`, same reason) and re-run for the VERBATIM GREEN summary line. End
     the report with the toplevel, the porcelain, every test file created RELATIVE TO `<worktree>`,
     the VERBATIM RED line, and the VERBATIM GREEN line (the GREEN line is also this step's own
     final full-suite summary — no separate third run needed).
     ACCEPTANCE CONDITION, non-negotiable: the GREEN summary line must be present and genuinely
     green (no `failed`, no `error`, no `ImportError`/collection error) — red/missing/unrunnable ⇒
     PARK `tests-red`. SEPARATELY, non-negotiable: both the RED line and the GREEN line for the
     falsifiability probe must be present, and the RED line must actually show a failure — either
     line missing, or the "RED" line not actually red, ⇒ PARK `falsifiability-unproven`. Record the
     WORKTREE path under the `worktrees` heartbeat key — a PARKED lane's worktree is deliberately
     left in place so the work survives (nothing here removes it). This is distinct from a lane
     that goes on to commit successfully: that worktree IS torn down, at (e).10 below, once its
     diff has actually landed. Neither park is a strike.
  6. RE-SNAPSHOT AND CLASSIFY. Diff against (d).1's baseline, then CLASSIFY — do NOT park on "any
     new entry": live sessions run alongside this job by design, and at cadence time the ordinary
     case is another session touching something. The rule: a new entry that intersects the item's
     declared `paths` OR the worktree porcelain ⇒ PARK `main-tree-leak` (a genuine leak is by
     construction in the item's own files). Every other new entry is concurrent-session activity
     ⇒ record under `live_state`, name no leak, continue.
     EXACT-LIST CHECK, run alongside and independent of the main-tree diff: cross-reference
     test-writer's own reported created-file list against that same report's worktree porcelain.
     Normalize first (strip a leading `<worktree>/`). A reported path that is neither
     worktree-relative nor resolves under `<worktree>/` ⇒ PARK `main-tree-leak`. Any normalized
     reported path absent from the worktree porcelain ⇒ PARK `main-tree-leak` naming it.
     RESIDUAL, stated honestly: this detects only what test-writer REPORTS; an unreported stray
     main-tree write is bounded downstream by (e).1's tests-missing positive check, not here.
     DOUBLE-CLASSIFICATION GUARD: subtract the exact-list check's flagged paths from the
     concurrent-session set before writing `live_state`, so one path is never both a leak and
     ordinary activity in the same heartbeat.

(e) INTEGRATE. Each Bash call is a fresh shell — substitute literal absolute paths everywhere,
never `$VAR` (an unexpanded `$VAR`, an unquoted `$(...)`/backtick, or a leading `~` after `--` is a
gate 3b `unresolvable-pathspec` denial — from `precommit_review_gate`, NOT gate 3 — that no review
recording can ever clear). ONE GIT COMMAND PER BASH LINE — never mix a git command with a
quote-heavy `printf`/`echo`/heredoc; gate 1 denies a compound it cannot tokenize.

  1. ENUMERATE in the worktree BEFORE any staging. The ENUMERATED SET is exactly
     `git -C <worktree> status --porcelain -z -uall`'s entries (modified + untracked + deleted +
     renamed; a rename contributes BOTH paths), never an agent's remembered list. RECONCILE
     against the IN-SCOPE UNION — members only:
       (i) the item's declared `paths`;
       (ii) this repo's TEST ROOTS bound to this item — any `tests/` dir under `modules/<name>/`
            for each module actually appearing in the declared paths, plus any `tests/` dir under
            a non-`modules/` top-level dir in the declared paths, plus `integration_tests/<SUBJECT>/`
            and `shared/tests/`; read `<name>` STRICTLY as "a module the item declared," NEVER
            "any module";
       (iii) `.secrets.baseline`;
       (iv) any path listed in `wheel_repos.json`'s `mandatory_registration_paths[]` for this
            slug (e.g. Agency's `scripts/ci/test_shards.py`, whose ROOTS list must gain any new
            test directory or nothing collects it — that file is none of (i)–(iii), so without
            this fourth named union member a lane that correctly registers its test dir would
            self-park `out-of-scope-content` on its own mandatory obligation; CSA's list is
            empty).
     Anything outside ⇒ PARK `out-of-scope-content` — never integrate a hand-picked subset, never
     widen the item's scope.
     POSITIVE CHECK: the ENUMERATED SET must contain at least one path under the (ii) test roots —
     zero ⇒ PARK `tests-missing`. A green pytest summary at (d).5 does not prove the tests landed.
  2. STAGE INTENT once: `git -C <worktree> add --intent-to-add -- <the UNTRACKED paths only>` —
     never the full set. The rc=128 trap is a pathspec token matching nothing in worktree and
     nothing in the index.
  3. PATCH to a DURABLE location outside the repo:
     `git -C <worktree> diff HEAD --binary --find-renames -- <the ENUMERATED SET> >
     <RUN_SCRATCH>/<slug>-<issue>-<UTC-stamp>.patch` (`<slug>` = the literal WHEEL_SLUG value from
     WRAPPER CONTEXT), then make it durable with
     `<SINK> patch --name <slug>-<issue>-<UTC-stamp>.patch --from <that file>` (create-only, at
     `~/.claude/schedules/patches/<name>`; the path the sink prints is what the heartbeat records).
     `<abs patch>` below means the byte-identical RUN_SCRATCH copy.
     Keep `--find-renames` explicit — never rely on the host's `diff.renames` default.
  4. CLAIM + GUARD: the fresh claim per (c) on `CLAIM_SET_ABS`, then
     `git -C $WHEEL_REPO status --porcelain -z -uall -- <CLAIM_SET_REL>` MUST be empty; any output
     ⇒ PARK (release the claim). `.secrets.baseline` is in both deliberately: it is in the commit
     pathspec from the outset, and `git commit -- <pathspec>` commits the working-tree content of
     every named path, so a concurrent baseline edit would otherwise ride along unnoticed.
  5. APPLY, in ONE Bash call chained with `&&`: the identical porcelain check again, AND
     `git -C $WHEEL_REPO apply --check <abs patch>`, AND `git -C $WHEEL_REPO apply <abs patch>`.
     The re-check shrinks the guard→apply window to milliseconds (mitigation only; step 6's undo
     is the actual safety property). Any failure ⇒ PARK; a failed `--check` leaves the tree
     untouched. Never `git apply -3`, never retry blind.
  6. VERIFY, with a NON-DESTRUCTIVE undo. `add --intent-to-add` the patch's untracked paths only
     (never a deleted or rename-away path — intent-adding a deletion STAGES it and (e).7's plain
     add then exits 128), recompute `git -C $WHEEL_REPO diff HEAD --binary --find-renames --
     <ENUMERATED SET>` and byte-compare to the patch file. Mismatch ⇒ undo with
     `git -C $WHEEL_REPO apply -R <abs patch>` then
     `git -C $WHEEL_REPO restore --staged -- <ENUMERATED SET>` — reverse-applies exactly what we
     applied and PRESERVES the other session's edit. NEVER `restore --source=HEAD --worktree`,
     proven to destroy a concurrent session's uncommitted work. If `apply -R` itself fails ⇒ PARK
     without touching the tree, release the claim, and NOTIFY per the preamble.
     POST-APPLY UNDO — A STANDING RULE: from the moment (e).5's apply succeeds, every park branch
     through the end of (e).8 — (e).7's rc=128, and 8a/8b/8c/8d/8e alike — MUST first run this
     undo, in this order, one git command per Bash line, THEN release the claim, THEN park.
     Nothing is lost: the patch is durable on disk and its path goes in the heartbeat. Skipping it
     leaves unreviewed or blocker-laden content applied and staged overnight, owned by nobody with
     the claim released — poisoning the next item's (a) DIRTY-SKIP and (e).4 clean-guard. The ONLY
     branch that must NOT undo is (e).9's post-commit confirmation failure — that content has
     landed, there is nothing applied to reverse, and gate 1 blocks `reset` anyway. If `apply -R`
     fails on ANY of those later park branches too, apply this SAME rule: PARK without touching the
     tree further, release the claim, and NOTIFY — never retry `apply -R` blind.
  7. STAGE for the pre-commit framework:
     `git -C $WHEEL_REPO add -- <the ENUMERATED SET — DELETIONS AND RENAME-AWAY PATHS INCLUDED>`,
     the whole set, no exclusions. `git apply` without `--index` never touches the index, so an
     applied deletion sits UNSTAGED (` D`) — exactly the state the pre-commit stash destroys, and a
     plain `git add` of that unstaged deletion exits 0 and stages it correctly. If THIS step itself
     exits 128, a deletion was already staged upstream by a stray intent-add ⇒ run (e).6's
     POST-APPLY UNDO, release the claim, and PARK `stray-intent-add` with the patch path in the
     heartbeat — never drop paths from the set to make it pass.
     ORDER, NOT NEUTRALITY, is what keeps this safe for gate 3b: the digest is computed AFTER
     staging (at (e).8's recording), and NOTHING stages between there and (e).9's commit, so the
     recorded key and the commit-time key agree. NEVER reorder to record before staging. The sole
     sanctioned exception is an active (e).8b hook-rewrite retry re-staging exactly the rewritten
     paths.
  8. REVIEW — reviewer-of-record selection is computed here, deterministically, never left to the
     lane's own judgment. Dispatch `trust-architect` INSTEAD of `code-reviewer` (substitution,
     never stacking) when the item touches any path in `wheel_repos.json`'s `trust_surface_prefixes`
     for this slug, otherwise `code-reviewer`. CROSS-CHECK before dispatching: run
     `python3 ~/.claude/hooks/review_risk_tier.py <the full pathspec about to be committed>`; if it
     returns `high` and this job's own `trust_surface` computation above was FALSE, escalate to
     `trust-architect` anyway and record a heartbeat finding `reviewer-routing-disagreement` — a
     wrong `trust_surface_prefixes` entry would otherwise silently route a trust-surface change to
     the wrong reviewer, with no other detector anywhere in this job. This adds no new gate; it
     reuses a classifier that already exists.
     RECORD THE ROUND-1 REVIEWER'S IDENTITY immediately after this `Agent` dispatch call returns —
     its own result carries both values — into this SAME lane's heartbeat/state entry, alongside
     the existing `{issue, stage, worktree, patch, review_key, strikes, park_reason}` fields:
     `reviewer_agent_id`, `reviewer_tool_use_id`. A warm round 2 (see WARM/COLD ROUNDS below) reads
     these back from that same entry — never retyped, never re-derived from a transcript.
     Record the reviewer's ACTUAL outcome with
     `python3 ~/.claude/hooks/record_review.py $WHEEL_REPO --pre-commit --clean --item <issue#>
     --reviewer <the dispatched agent type> --reviewer-agent-id <the recorded reviewer_agent_id>
     --reviewer-tool-use-id <the recorded reviewer_tool_use_id> --paths <the ENUMERATED SET>
     .secrets.baseline < /dev/null` — or `--blockers <n>` in place of `--clean`. The stdin redirect
     is MANDATORY. `--paths` is variadic so it goes LAST, and its list must be the CLAIM SET —
     byte-identical to (e).9's commit pathspec. The three `--reviewer*` fields are the reviewer's
     IDENTITY — the SAME `reviewer_agent_id`/`reviewer_tool_use_id` values this step just recorded
     into the lane's own heartbeat/state entry, never retyped or re-derived — and they are what
     lets the recorder join `--reviewer-tool-use-id` to `~/.claude/.agent_budget/spend.jsonl` and
     write the model the reviewer ACTUALLY ran on (`model=<tier> model_source=ledger`). Omitting
     them still records, but logs `missing-reviewer-identity` and proves nothing about which model
     reviewed it.
     WARM/COLD ROUNDS: the default fix-round response is TARGETED FALSIFIABILITY VERIFICATION, not
     a repeated full review. When a full re-review is genuinely warranted, continue the round-1
     reviewer in-context (SendMessage), re-scoped to the FULL current pending diff — never "confirm
     the reported fixes." At most TWO consecutive warm rounds per boundary, then a COLD dispatch.
     Before every warm round, re-run `review_risk_tier.py` on the full current pathspec and
     re-derive the reviewer-of-record per the CROSS-CHECK above; if either changed, the warm chain
     BREAKS and the round is a fresh COLD round-1. Record a warm round with the full chain identity,
     `--warm` INCLUDED — omitting it silently disables the two-warm-round cap this paragraph just
     described, since `record_review.py`'s cap logic is gated entirely on that flag's presence:
     `--warm --round <n> --reviewer <type> --reviewer-agent-id <the recorded value>
     --reviewer-tool-use-id <the recorded value> --prev precommit:<digest>`, copied verbatim from
     this lane's heartbeat entry, never retyped — a single-character typo lands as a
     permanently-unmatched entry. A background/worktree-isolated dispatch's continuability is
     UNVERIFIED — treat a failed continuation as non-continuable and go COLD, never improvise.
     8a. REVIEW RETURNED BLOCKERS: record `--blockers <n>`, run (e).6's POST-APPLY UNDO, release
         the claim, PARK `review-blockers` with the patch path and blocker count. Do NOT attempt
         the commit and do NOT re-review to talk the count down — `--blockers` makes gate 3b deny
         `review-blockers-unresolved`, a reason nothing else can clear. This is a REAL stop, not a
         log line: it is jidoka, authority actually exercised.
     8b. HOOK-REWRITE: if any pre-commit write hook rewrites a reviewed path after recording,
         re-stage exactly the rewritten paths (the ONE sanctioned exception to (e).7's ordering
         invariant), re-review, re-record, retry — AT MOST 3 TIMES total. Still failing after the
         third ⇒ POST-APPLY UNDO, release, PARK `hook-rewrite-loop`. A capped park, not one of the
         job's 3 strikes.
     8c. GATE-4 (commit-mutex/claims) denial: if it names `wheel-$WHEEL_SLUG-<item>` as the
         contesting holder, the (c) release was skipped — release it first, then retry the
         IDENTICAL command. If it names any other holder, wait ~45s and retry, AT MOST 3 TIMES.
         Still denied after the third ⇒ POST-APPLY UNDO, release, PARK `commit-contested` naming
         the holder.

     CLAIM SET. TWO SEPARATE checks; never folded into one porcelain read:
     (1) `.secrets.baseline` DRIFT — `git -C $WHEEL_REPO status --porcelain=v2 -z -uall --
         .secrets.baseline`. Note `=v2`, a deliberate one-off deviation from every OTHER porcelain
         read in this recipe (all of which use v1): a `-z` v1 rename record splits into an
         unprefixed OLD-path field with no status code, and a parser that naively reads a record's
         first two characters as a status code gets a false non-blank hit on ordinary path text —
         `--porcelain=v2`'s rename records carry an explicit `2` line type with both paths tagged,
         so this one read is never the ambiguous kind. NEVER "simplify" this back to v1 to match
         the rest of the recipe — that is precisely the false-positive this deviation exists to
         avoid. Non-empty ⇒ POST-APPLY UNDO, release, PARK `baseline-drifted` —
         UNLESS this item's own hooks already rewrote it, or this is inside an active 8b retry for
         that exact rewrite.
     (2) ENUMERATED-SET DRIFT since (e).6 — RE-RUN (e).6's own recompute verbatim and byte-compare
         to the durable patch. Mismatch ⇒ POST-APPLY UNDO, release, PARK `concurrent-edit-window`

     `git -C $WHEEL_REPO commit -F <msgfile> -- <the ENUMERATED SET, INCLUDING a rename's OLD
     path> .secrets.baseline` — `-F <msgfile>`, msgfile written into RUN_SCRATCH by a separate prior Write-tool call,

     Four rules on that line: (i) the `--` is MANDATORY; (ii) NO redirects — an appended `2>` is
     tokenized INTO the pathspec, poisoning gate 4's claimed set and gate 3b's digest, and a
     redirect the shell actually executes can make gate 3b FAIL OPEN, landing an unreviewed commit
     silently; (iii) no heredoc, no `-F -`; (iv) the pathspec must be byte-identical to (e).8's

     `git -C $WHEEL_REPO status --porcelain -z -uall -- <ENUMERATED SET> .secrets.baseline` must
     be empty. A green exit alone is not evidence anything landed. Confirmation failure ⇒ do NOT
     retry (a half-landed commit cannot be un-landed; gate 1 blocks `reset`): NOTIFY, ensure the
